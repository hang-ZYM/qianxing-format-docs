# 关卡的逻辑：意图层与结构层

> **读者为什么需要知道这个** —— 动手之前先分清两件事：**这个关卡要成为什么**（意图层），和**它由什么搭成**（结构层）。前者答不上来，你会在技术细节里迷路；后者列不出来，你的意图就永远停在想法里。这一篇是右岸（项目侧）的第一篇，也是后面"模块化""任务分解"两篇的地基——不读它，后面讲的"模块"和"任务"没有可挂靠的对象。

**前置**：[03 两岸一桥](03_两岸一桥.md)。这一篇展开的是它右岸的那一半。

---

右岸处理的是**我们自己的项目**，不是别人的系统。所以本篇讲的每一条都是**设计主张**，不是可以证伪的事实——它没有证据等级，只有"好不好用"。

这一点和左岸正相反：左岸的结论都带证据等级，因为它在说"世界长什么样"；右岸给的是理由，因为它是"我们决定怎么搭"。两种写法本身就在提醒读者该信到什么程度（对照 [03 两岸一桥](03_两岸一桥.md) 第二节）。下面凡涉及游戏侧事实的地方，仍照旧标出等级。

## 一、意图层 · 这个关卡要成为什么

意图层回答"为什么做这个关卡"。它由五项构成：

| 项 | 是什么 | 怎么记 |
|---|---|---|
| **玩法内核** | 一句话说清玩家在干什么 | 写成一句"玩家在〔条件〕下〔动作〕"，句里必须有动词和一个压力来源；一句话说不完，就是还没想清。 |
| **玩法循环** | 一轮里发生什么（节奏单元） | 按时间顺序列"一轮"的几段（每段配触发或时限），只写节拍，不写数值。 |
| **情绪曲线** | 什么时候紧、什么时候松 | 以轮次或阶段为横轴，标出"紧／松"的位置和转折点（量化记法见"未确定项"）。 |
| **胜负线** | 什么算赢、什么算输、什么时候结算 | 三句话：胜利条件句、失败条件句、结算时机句。三句之外都是解释。 |
| **不可让步的设计约束** | 定了就不许为了省事绕开的那几条 | 用"必须……"句式写下，并各配一句"若绕开，关卡会退化成什么"。 |

前四项是**描述**——描述这个关卡是什么样。第五项是**约束**——它不描述关卡，它反过来规定关卡里什么可以做、什么不可以做。所以它要单独讲。

### 「不可让步的设计约束」为什么单列

> 它是最硬的一根钉子。**它一旦定下，后面所有的技术选择都是被它逼出来的。**

举一个方法层面的例子（只讲取舍，不讲成品）。某夜战关卡定下一条约束：**光 = 视野**——怪只靠灯光可见；灯照不到的地方，怪在玩家眼里就不存在。

这一条不是美术偏好，是玩法前提。写定之后，它逼出了三条各自独立的技术线：

- **雾的可见距离** —— 要让"看不见"成为空间上的事实，环境里得有一层能压缩视距的雾（远雾点距离、浓度、雾色这几个旋钮）。字段为**字节实证**，并有**人工核验**（用户实机定案过雾色）；完整落位见 [03 两岸一桥](03_两岸一桥.md) 第三节。
- **关卡时间推进** —— 要让"守到天亮"成立，关卡得有会流动的时间，环境光照按时点表自动采样。字段为**字节实证**，"时间会真的流动"为**人工核验**。
- **单位状态隐身** —— 要让怪真的"不显示"，得给怪一个隐藏单位状态，再由灯的照明范围触发显示与隐藏。字段与节点为**字节实证**；整条链**尚未实机验证**。

三条线的共同点：它们都不是"为了让画面好看"，而是**被那条约束逼出来的必需项**。约束在前，技术选择在后——这个顺序不能反。

反过来看：如果当初为了省事绕开这条约束——比如"怪一直可见，灯光只做氛围"——那么这三条技术线一条都不需要，整个关卡会退化成一个普通的打怪关：光还在，但它不再是玩法，只剩下美术。

**这就是它要单列的原因。** 列出来，读者才知道后面所有的技术选择不是拍脑袋，是被一条明确的约束推着走的；也才知道**这条约束一旦松动，会有多少东西跟着塌**。

## 二、结构层 · 它由什么搭成

意图层答"为什么"，结构层答"有什么"。结构层把场景里所有东西分成四类。分类的目的不是学术整齐，是让这份清单**能用来分工、能用来查漏**——缺了什么、该在哪一类里补，一眼能定位。

### 2.1 场地

关卡赖以存在的空间本身。

- **包含**：整幅范围、区域划分（哪些区域是什么性质）、坐标系与原点、锚点（关键位置）。
- **特点**：它是"不可动的底"。别的一切都相对它定位，所以它应当最先定、且定了尽量不再动。
- **左岸落点**：关卡的坐标与位姿字段，以及地面／地形相关域（具体见 04 篇与第四部分）。

### 2.2 构件

场景里所有"东西"——名词。能看见、能摆放、能被引用。它分四小类：

| 小类 | 是什么 | 备注 |
|---|---|---|
| **复合构件**（场景基本单元） | 可以**整体操作**的一组件 | 见下 |
| **实体** | 单个具体对象，场景里的"一份" | 号在 `0x404`／`0x408` 段（**字节实证**） |
| **元件** | 预先做好的物件模板（游戏版的预制件 Prefab） | 落在关卡的模板段（**段号有两个内部来源互相冲突，暂无权威可仲裁，故不落号**）；元件双号制见 [术语表](参考_术语表.md) §3.1 |
| **纯装饰** | 只负责观感、不承担机制的件 | 与承担机制的件分开列，便于分工 |

**为什么需要复合构件。** 因为有些件要**整体操作**——一起摆放、一起移动、一起复制。单个实体做不到这件事：你没法把"一座塔"当成一件事来搬或来复制，只能一个一个地选中那十几个件，再确认没有漏掉一个。

复合构件把一组件收进一个单元，操作的单位从"件"变成"单元"。它的构造是三样东西合成：

- 一个**模板**（元件）——这组件的定义；
- 一个**实例**（主件实体）——盖在场景里的那一份；
- 一张**摆放表**——组内每个件相对主件的位置。

三样东西各自都在左岸有位置——元件模板 / 主件实体 / 主件 `f6` 槽 `cid61` → 载荷 `f65` 的摆放表条目，[03 两岸一桥](03_两岸一桥.md) 第三节最后一行给了这条落位。但把它们合读成"一个可整体操作的单元"，是**推断**——公开定义尚未合成（[术语表](参考_术语表.md) §1.4 把"复合构件"列为待定词，定义待补）。

也正因为它建立在"模板 + 实例"上，复合构件有一个副作用：**改一处模板，所有实例跟着变**。这是它相对逐件摆放的根本好处，也是它的风险来源（改错一处，全场遭殃）。这一条是我们的读法，标**推断**。

### 2.3 机制

场景里所有"行为"——动词。它包含六类：

| 机制 | 管什么 |
|---|---|
| **路径** | 东西怎么走 |
| **触发** | 什么条件下，发生什么 |
| **状态** | 对象此刻处于什么情况 |
| **时间** | 什么时候推进什么 |
| **光照** | 什么被看见 |
| **水体** | 哪里有水、水怎么动 |

- **左岸落点**：节点图、组件、环境块（具体见 04 篇）。
- **为什么机制独立成类**：因为机制是**行为**，构件是**东西**，两者的建造方式完全不同。构件靠**摆放**——摆到位就完了；机制大量靠**图与组件**——要连节点、配参数、走运行逻辑。混成一类，清单就没法分工：你分不清某一项出了问题，是该挪个位置，还是该去查一段逻辑。

### 2.4 资产

非空间性的素材。

- **包含**：**图**（节点图）、**环境**（光照／时间／天气的配置）、**特效**、**音效**。
- **与机制的接口**：机制的载体是图与组件；而"图"本身作为一份可保存、可挂载的文件，归在资产类。同一样东西，从"行为"的角度看是机制，从"它是一份素材"的角度看是资产——这是两种视角，不是两样东西。
- **左岸落点**：图库（挂载）、环境块、特效域、音效域（见 03 与第四部分）。

## 三、两层的关系

第一件事：意图层往下**逐层具体化**。

```
意图层   这个关卡要成为什么         （为什么）
   │  逐层具体化
结构层   它由什么搭成               （有什么）
   │
处理层   怎么把它造出来             （怎么造）  ← 06 模块化 / 07 任务分解
```

每往下一层，问题都更具体、更接近能动手做的程度：意图层是一句话，结构层是一份清单，处理层是一串可验证的步骤。本篇只到结构层为止；处理层是下一批文档的事。

第二件事，也是右岸与桥的接口：**结构层里每一个东西，最终都要在左岸找到一个落点。**

| 结构层这一类 | 去左岸找什么 |
|---|---|
| 场地 | 坐标与位姿、地面／地形 |
| 构件 | 实体域、元件域、布设组 |
| 机制 | 节点图、组件、环境块 |
| 资产 | 图库、环境块、特效与音效域 |

找不到落点的结构项，就是**一个还没法造出来的愿望**——它也许有办法实现，但我们还不知道在哪实现。这正是 04 篇《对齐》要干的活：拿结构层这份清单，逐项去左岸找位置，找到的写下落位，找不到的记成待查。

一句话：**结构层是意图层的落地清单，桥是这份清单的可行性检查。**

## 可验证的把手

给一个能照做的练习。拿一个你想做的效果，按顺序写两页。

**第一页 · 意图层**
1. 玩法内核：一句话，玩家在干什么？（动词 + 压力来源）
2. 玩法循环：一轮里发生什么？（按时间列几段，只写节拍）
3. 情绪曲线：什么时候紧、什么时候松？（标位置与转折）
4. 胜负线：什么算赢、什么算输、什么时候结算？（三句）

再补一句：这里有没有一条**不可让步的设计约束**？有就写成"必须……"，并写出"若绕开会退化成什么"。

**第二页 · 结构层**
把实现这个效果需要的东西，分别填进 场地／构件／机制／资产 四类。某一类填不出来，往往说明那一层你还没想。

**检查清单**（这才是练习真正的部分）：
- 结构层每一项，能追到第一页的某一条意图吗？追不到的，或是多余的，或是哪个意图没写清。
- 第一页每一条意图，在结构层有承载它的项吗？没有的，或是空想，或是结构还缺一类。

两边都对上，清单才算**闭合**。这份闭合的清单，就是 04 篇对齐表的输入——每一项拿去找左岸的落点。

## 未确定项

- **情绪曲线的记录方式**：目前只写成"紧／松"的位置，没有量化或结构化的格式（怎么记、记成什么，未定）。
- **"不可让步的设计约束"该在什么时机定下**：项目开始时定，还是设计细化后定，还没有固定流程，也没有反例检验。
- **"复合构件"的公开定义**：术语表列为待定词（开源仓零命中），尚未在公开文档里合成一句正式定义（与 03 第三节同一处未定项）。
- **意图层五项是否够用**："可复玩性""单局时长目标"等等，目前或并入玩法内核、或散在别处；五项是不是完备，未检验。
- **"玩家"算不算结构层的一类**：目前把玩家／角色当作平台默认物，不单列。这个处理对不对，未有定论。
- **结构层四类的完备性**：四类是从项目里试出来的，还没有"某个东西四类都装不下"的反例来检验它。
- **两层之间的映射粒度**：一条意图往往对应结构层多项（如"光 = 视野"对应三条技术线），反过来也成立——目前没有固定的对应写法。（待补）

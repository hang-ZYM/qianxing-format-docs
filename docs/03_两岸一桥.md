# 两岸一桥：对「游戏」的处理 与 对「项目」的处理

> **读者为什么需要知道这个** —— 这是理解后面所有内容的地图。读完这一篇，你会知道这个项目同时在处理两种性质完全不同的东西、它们为什么必须分开讲、以及为什么真正难的是两边中间那一段。不读也能看后面的字段表，但会分不清哪些是"世界的事实"、哪些是"我们的选择"。

**前置**：无。本篇是第二部分的入口；只想看梗概的话 [00 设计说明](00_设计说明.md) 已经给出框架，本篇是它的展开。

---

## 一、两侧分别是什么

这个项目同时在处理两个对象。它们的性质不同，所以分成两侧讲。

### 左岸 · 对「游戏」的处理

对象是**那个封闭系统**——千星奇域本身。

它没有 SDK、没有公开文档、没有源码（**人工核验**：官方渠道不提供这些）。我们唯一能对它做的事，是**读懂它的数据格式，然后按它的规矩写出它认得的字节**。

所以左岸的内容是描述性的：容器怎么摆、字段号是什么、组件落在哪个槽、图头类别取什么值。**你不是在设计它，你是在发现它。** 它已经在那里了，你只能把它的样子读准。

### 右岸 · 对「项目」的处理

对象是**我们自己的关卡项目**。

一个关卡要成为什么、由什么搭成、怎么拆成可以分别验证的步骤——这些没有唯一答案，是我们自己定的。**模块化**（把产物拆成可复用的单元）和**任务分解**（把过程拆成可验证的步骤），都是"处理项目"的手段，不是目的。

### 桥 · 对齐

两侧之间靠**对齐**连着：**右岸的每一个设计决定，都要落到左岸某个可行位置上。**

"可行位置"是关键词。它不是"落到某个字段"这么简单，而是那个位置真的能让游戏做出你要的事。找不到可行位置，右岸的决定就只是一句话。

对齐有两个方向，走的是同一条桥：

- **落位**：右岸已经定了一个设计，去左岸找它能落在哪。这是主要的走法——"我要怪隐形"，去查单位状态和模型显示。
- **问路**：左岸挖出一个位置，回头看右岸能不能用它。这是被动的走法，但同样重要——挖字段的时候常常会挖出"原来还能这样"，反过来改右岸的设计。

两个方向都会发生，这也是桥必须显式写出来的原因：如果只有一侧的文档，"问路"就无从谈起——你不知道有哪些位置可问。

### 为什么用"两岸一桥"来解释这件事

这套分法不是为了好看。它解释三件事：

1. **它解释了这个项目真正的形状。** 干的活就是两端——一头读游戏，一头组织项目——中间靠映射连着。说"我们在做千星逆向"或"我们在做 AI 创作"都只说了半边。
2. **它解释了为什么难。** 难不在写代码，在两侧粒度对不上（第三节展开）。
3. **它让"开什么、闭什么"有了自然边界。** 左岸是别人的系统，右岸是自己的方法，界限本来就在那里，不用另外划。

## 二、两侧的性质完全不同（本篇第一个核心洞见）

| | 左岸 · 对游戏的处理 | 右岸 · 对项目的处理 |
|---|---|---|
| 对象 | **别人的**封闭系统 | **我们自己的**关卡 |
| 能动性 | 只能**发现**——读懂它、按它的规矩写 | 可以**发明**——怎么设计、怎么拆、怎么组合，自己定 |
| 动作 | 译解 / 适配 | 设计 / 构造 |
| 变化速度 | 字段随游戏版本变 | 架构相对稳定 |

一句话立起来：

> **左岸是"理解"，右岸是"设计"。左岸你只能发现真理，右岸你可以创造结构。**

这句话不是口号，它决定四件事：

1. **左岸的结论可以被证伪，右岸的结论只能被取舍。** 左岸说"这个字段是远雾点距离"，它要么对要么错，可以用字节和实机去判；右岸说"关卡分意图层和结构层"，这不是真假问题，是它好不好用的问题。所以两边对"证据"的要求不一样——左岸的每条断言都要标证据等级，右岸要给的是理由。
2. **左岸的知识会过期，右岸的不会那么快。** 游戏更新一次，字段可能换位、混淆名可能重生成；而"怎么把一个复杂创作拆成可验证的模块"这件事，不随版本变。
3. **混在一起写，读者会分不清该信到什么程度。** 一份文档里如果"字节实证的字段号"和"我们的设计主张"长得一样，读者就没法判断哪些能拿去改、哪些不能。
4. **两侧要的"把握"不同。** 左岸要的是"有多确定"——这条是字节读出来的，还是我们推的，差很多；右岸要的是"为什么这么定"——它的价值在理由，不在确定性。把两种"把握"混在一起讲，两边都会失真。

（把两侧混着讲的后果，见 [00 设计说明](00_设计说明.md) 第二节。）

## 三、桥为什么难：两侧的粒度对不上（本篇第二个核心洞见）

困难不在于"写代码"。困难在于**右岸一个愿望，左岸可能是一整串字节操作**。

下面这张表是本篇最实的一部分。左边是我们能一句话说出口的设计决定，右边是它在字节层真正的样子。第四列标明这一条的凭据——这是本仓库对外最坚持的一件事：不把推测写成事实。

| 右岸（我们的设计决定） | → 落到 → | 左岸（游戏的可行位置） | 这一条的凭据 |
|---|---|---|---|
| "怪要隐形，进灯圈才显形" | → | 单位状态壳（实体 f7 槽 cid14 → 载荷 f24）+ 三处注册（f15 定义 / f16 副本 / f6 资源树 cat11）+ 状态图（图头类别 20003）+ 入口节点（kernel 300「状态变更时」/ 299「状态结束时」）+ 目标实体（节点 308「激活 / 关闭模型显示」的入参） | 字段与节点为**字节实证**；"进状态即触发 300"为**推断**；整条链**尚未实机验证**（对照件已出，待人工目视检查） |
| "让玩家看不远" | → | 远雾点距离（f75.f1.f3 → 天气配置 → f51.f17，一个字段）+ 浓度（f18 / f19，逐项对号**推断**）+ 雾色（f51.f15 / f16 / f20 的 base）+ 开关（f75.f1.f3 里有没有 {f1,f2}；随时间自动切换 = f51.f25） | f51.f17 与浓度字段为**字节实证**（同名作者预设里"望远"=3000、"挡视线"=200 单调对应），并有**人工核验**（用户实测 f17=40 生效）；雾色为**人工核验**（用户实测定案纯黑 `0xFF000000`）；"天气类型当前只支持雾"为**官方文档** |
| "守到天亮" | → | 环境光照曲线（时点表，游戏按当前时间自动采样）+ 关卡时间设置（f11.f1.f17 初始时间点 + f11.f1.f18 每秒流逝分钟） | 字段为**字节实证**；"时间会真的流动"为**人工核验**（用户导入后目视确认） |
| "一个能整体操作的场景单元" | → | 预制件组：定义体（元件，`.gia` 方言，落在关卡的模板段）+ 实例（主件实体，f5 放置实体）+ 摆放表（主件 f6 槽 cid61 → 载荷 f65：成员的位置与旋转） | 定义体↔实例的双号制、摆放表条目为**字节实证**；**元件所在段号的两个内部来源互相冲突、无权威可仲裁，故此处不落段号**；把三者读作"一个可整体操作的单元"是**推断**（内部对象模型的读法，尚未在公开文档里合成一句定义） |

读这张表要注意三点：

- **每一条右边都不止一个东西。** "看不远"看起来是一个愿望，落到字节上是四个独立旋钮（距离、浓度、雾色、开关），各在各的字段、各自会单独失效。少写一个，效果就不对，而且不一定报错。
- **粒度差是数量级的。** 右边那一列，短的是一条字段，长的是"状态壳 + 三处注册 + 一张图 + 两个节点 + 一个目标"。**右岸一行，左岸可能是一整天。**
- **粒度对不上，会连带影响"出错之后怎么办"。** 一次改一整个愿望，如果没生效，你不知道是四个旋钮里哪一个错了；把愿望拆成"改一个字段、验一次"的步骤，错在哪一步就定位到哪一步。所以右岸讲的任务分解不是项目管理习惯，它是粒度差直接逼出来的应对。

结论句：

> **粒度对不上，桥就是断的。右边是一个愿望，左边是一串字节，中间那段就是我们要干的活。**

所以这个项目真正的工作量不在两端，在中间那段的逐条对齐上。后面 04 篇（对齐表）是这段活的主体；右岸三篇（05–07）讲怎么把这段活拆开做、每步怎么验证。

## 四、和"开放边界"的关系

两侧性质不同，也决定了**哪部分能公开、哪部分不能**（完整的开/不开边界见 [00 设计说明](00_设计说明.md) 第六节）。其中一条与两侧性质直接相关，单独说明：

- **桥面的纪律可公开。** 走在桥上要守的规矩——证据优先级的排法、单变量对照、失败怎么记——属于方法，和右岸工程层一样可公开。它回答的是"怎么保证每一步是真的"，不涉及任何一关的具体内容。

判据一句话：**拿出来能让任何人照着用的，开；只对做我们这一关有用的，不开。** 边界明确写出来，读者才知道有些事这里为什么不讲。（完整边界见 [00 设计说明](00_设计说明.md) 第六节。）

这里有一条值得单独说明的取舍。左岸公开的是**别人系统的数据格式**，合规上有不确定性；右岸公开的是**我们自己的工程方法**，风险低得多。如果只开左岸、不开右岸，等于把风险高的发出去、风险低的藏起来，而且发出去的还只是"搬运"——左岸读得再准，本质上仍是发现别人的东西。所以这份文档把重心放在右岸的方法上：左岸给它事实，右岸给的是能迁移到别处的做法。

## 五、怎么用这张地图

这一篇给的是地图，不是路线。读完它，按你的身份挑一条走——三条阅读路径见 [00 设计说明](00_设计说明.md) 第五节（权威版本）。

三条路都会路过这一篇，因为**后面每一篇都是本篇某一侧的展开**：第二部分（03–04）展开桥，第三部分（05–08）展开右岸，第四部分（09–11）展开左岸，第五部分（12）讲走在桥上要守的纪律。

三条路对这张地图的用法不同：

- **创作者**只需要知道"右岸是我能填的部分，左岸是我要照着遵守的部分"，具体字段按需查。
- **AI / 自动化工程师**要的是骨架——两侧的性质差异决定了工程上为什么必须分模块、为什么必须每步可验。
- **逆向 / 数据开发者**从右岸得到"为什么要挖"（挖出来的位置要用来落什么），再进左岸的字节细节。

**别从头读到尾。** 这份文档的层数不浅，按身份挑一条走，比顺序读完省时间。

## 可验证的把手

本篇是概念篇，不产生可直接运行的命令。可以对照的实物有三处：

1. **两侧性质对照**放大看：左岸侧（第四部分）每个结论都带证据等级；右岸侧（第三部分）讲的是理由，不带等级——这两种写法本身就是两侧性质的体现，可以对照着读。
2. **第三节的四个例子**都已在真实文件里落地过：隐身怪（一件待人工目视检查的对照件）、雾与视野（一件只差雾距离的对照件，`f51.f17=40`）、时间流动（一件把时间设成 4:00 / 流速 10 的对照件，`f11.f1.f17=4` / `f18=10`）、元件与场景单元（元件包 + 关卡内 f5 实例 + 摆放表条目）。
3. **身份路径**：按第五节任选一条走一遍，能在第一站验证"这篇是不是你要的入口"。

## 未确定项

- **隐身怪整链未实机验证**：字段与节点均已字节定位，但"状态壳 + 状态图 + 308 节点"合起来能不能让指定实体真的消失，**待人工目视检查**（对照件已出）。标为"推断"的三处是：进状态是否触发 kernel 300、kernel 299 在状态结束时能否执行、308 的首试行为。
- **雾的"浓度"是哪个字段**：f18 与 f19 都被用户在实机里动过，逐项对号**未定案**（待补：单变量对照件）。
- **"一个可整体操作的场景单元"的合成定义**：定义体 / 实例 / 摆放表三者各自是字节实证，但把它们合成"预制件组"这一个概念的**正式定义尚未进公开文档**（待补）。
- **右岸工程层的公开形态**：本篇把"可公开"写成了原则，但对象模型 / 模块协议 / 任务分解执行模型目前还没全部整理成可发布文档（见 [00 设计说明](00_设计说明.md) 的诚实说明）。
- **左岸字段的版本敏感度**：左岸"随版本变"是一条性质判断（**推断**），具体哪些字段在哪些版本间变过、有一份清单（待补）。

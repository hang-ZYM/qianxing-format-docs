# 28 · 验证方法与发现

> 本卷是 [docs/06 验证方法论](06_验证方法论.md)的操作层补充：我们具体用了什么方法、
> 发现了什么、哪些路走不通。**只写方法与结论，不写实现细节**（范围声明见 README）。
> 证据分级同全库：[A]/[J]/[P]/[C]。

## 一、三层校验体系

### 1.1 架构

```
① 写入自校验   输出后立即重解析，字节必须一致（工具链内建，零成本）
② 规则校验     已积累实证规则的离线检查（工具链 verify）
③ 编辑器终审   装载行为为最终裁决（人工导入观察 + 重保存字节对比）
```

**闭环逻辑**：每件被编辑器接受的文件都是对工具链的传递性验证；每处被装载器修改的
差异都转化为新规则回填第②层——同一类错误此后离线拦截。离线校验面随实证积累扩大。

### 1.2 权限边界（重要发现）

离线判定不是万能的。通过系统性的对抗测试，我们测绘出明确的边界：

| 异常类别 | 离线可判？ | 原因 |
|---|---|---|
| 泛型信封缺失 | ✅ | 规则面可检 |
| kind5 引脚形态不完整 | ✅ | 规则面可检 |
| kernel 越界 | ✅ | 宇宙表可查 |
| 幽灵 kernel 引用 | ❌ | 结构合法但语义可疑——只有活体装载有裁决权 |
| 报文截断 | ❌ | 同上 |
| 重复节点 ID | ❌ | 同上 |
| 极端坐标 | ❌ | 同上 |

**结论**：四类异常离线全 PASS——"verify 通过"≠"装载通过"。这条边界本身是体系的一等
成果：知道自己不能判什么，与能判什么同等重要。

### 1.3 对抗验证（故障注入）

**方法**：系统性构造异常输入，观察装载器的拒绝条件——**被拒绝的才是真规则**。

平台不提供任何错误信息（静默降级律），对抗测试是无提示环境下唯一可靠的规则提取
路径。测试集覆盖三类历史失效形态 + 六类边界形态，全部复现"离线校验通过但装载后
内容丢失"的事故条件。

**结果**：全语料零误报；精确诊断到节点号级别。

## 二、运行时观察面

### 2.1 编辑器数据流的架构发现

| 发现 | 证据级 | 含义 |
|---|---|---|
| **编辑器不读取 .gil 文件** | [J] | 关卡数据由游戏侧推送进入会话——.gil 是游戏侧的持久化格式 |
| **单会话锁** | [J] | 第二个并发连接被立即拒绝——不存在多客户端并行操作的可能 |
| **.gia 日志写入者 = 编辑器** | [J] | 日志链路 = 运行时→传输→编辑器收集器→落盘；游戏内直接试玩不产生日志 |
| **勾选监听制** | [J] | 节点图执行日志须在编辑器中勾选目标图才记录；勾选每次会话重置 |

### 2.2 六个观察面

| # | 观察面 | 位置（通用路径） | 判读 |
|---|---|---|---|
| 1 | 游戏客户端日志 | `AppData\LocalLow\miHoYo\<游戏>\output_log.txt` | 开跑信号/平台行为 |
| 2 | Lua 脚本日志 | `BeyondLocal\<账号>\Beyond_Debug_Log\*.gia` | print 全量；一局一文件 |
| 3 | 节点图执行日志 | 同上 | 含**运行时引脚值**（变量行为唯一窗口） |
| 4 | 致命错误 | 关卡目录 `external_lua_file\ErrorLog.txt` | 循环调用/挂载失败 |
| 5 | 编辑器存档面 | `Beyond_Local_Save_Level\<地图ID>\` | 主件滞后，Temp 副本才新鲜 |
| 6 | 编辑器日志 | `<游戏安装>\BeyondAssets\BeyondAssistEditor\Log\log.txt` | 会话连接与状态机 |

详见 [manuals/17](../manuals/17_验证与日志手册.md)。

### 2.3 运行时判例（日志作为判决仪器的记录）

| 观测 | 通道 | 判过什么 |
|---|---|---|
| 打印字符串原样回读 | 执行日志条目 | 执行边通路（事件→动作完整链） |
| 变量名 + 运行时值 | 执行明细 | 变量寻址方式/黑板读写一致性/无值变量=默认 0 |
| 信号回执逐字核对 | 日志 + 客户端日志 | 信号链通路 + 注册时序约束（须在 OnInit 内） |
| 循环迭代数 × 轮次 | 执行明细 | 循环语义含端定案（1..N 含两端） |
| 多分支命中统计 | 执行明细 | 分支值匹配语义 |
| 节点存活数 | 装载差分 | 剥离检测（对抗验证的核心判据） |

### 2.4 采集纪律

1. **单变量原则**：一次试玩只验一批预写判据——拒绝"试一下看看"
2. **预写判据**：试玩前明确"看到 X = 判 Y"
3. **失败冻结**：连续两轮无进展强制停下，先穷尽本地可读源
4. 差分采集：试玩前记录基线 → 试玩 → 差分（新日志 + 增量 + 新局内数据）

## 三、快速验证（图域）

### 3.1 能力定义

**目的：秒级获得权威校验结论**——把"提交→等待装载→观察结果"的分钟级回路压缩为即时回路。

| 能力 | 做法（概念级） | 用途 |
|---|---|---|
| **判定读** | 将候选图构造提交编辑器自身的装载逻辑执行，回读节点级接受/剥离结果 | 最权威的离线后校验 |
| **热写** | 将候选内容置入当前工作画布，即时渲染 | 快速目检与端到端验证 |
| **监控读** | 周期性观测编辑器内容库的状态变化 | 定位官方装载的发生时刻 |

**能力域边界**：仅覆盖图节点域——实体与地形的数据在游戏进程，编辑器内无对应数据
模型，因此无此通道（走文件级冷通道）。

### 3.2 安全约束（原则级）

- 只操作当前工作画布，不影响关卡其他内容
- 整关级操作禁用（曾导致用户其他图内容丢失，事故后立为铁律）
- 遵守宿主线程模型

### 3.3 验收记录

1. 注入产物装载接受率全绿（八格验收矩阵）
2. 保真验证：12 节点图移植后与原版一致——用户确认
3. 全合成验证：从零合成"事件→打印"图注入成功——用户确认
4. 持久性：保存后退出重进，内容存活

**注**：此能力的实现方法不在本仓库范围（见 README 诚实声明 #5）。

## 四、负结果档案（走不通的路）

| 路 | 结果 | 判例价值 |
|---|---|---|
| 伪装并发客户端 | 拒绝（单会话锁） | 内容推送需求改走官方导入通道 |
| 编辑器进程主动拉起 | 三连证伪（会话绑定 + 单实例 + 后连拒） | 定案：用户启动编辑器为唯一人工环节 |
| 异步 I/O 拦截（.NET 8） | 失败（运行时代码生成错误） | 此栈限制对同类项目有参考价值 |
| 编辑器 UI 自动化 | 判定不可走（合规+技术） | 确立红线 |

**负结果的价值**：记录"走不通"与记录"走通"同等重要——防止后续重复投入。

## 五、方法论总结

| 原则 | 内容 |
|---|---|
| **以编辑器产物为参考实现** | 不重新发明格式；工具只承担"改对位置"的责任 |
| **以编辑器行为为校验器** | 装载行为是唯一权威；差分/负向/重保存三法把行为转译为规则 |
| **先建判定，后建生产** | 规则先行让生产线自带可解释的质量门 |
| **判定体系必须测绘自身权限边界** | 不能判什么与能判什么同等重要 |
| **故障注入是对抗静默失效的标准手段** | 无错误信息的系统，拒绝边界即规则 |
| **分域而治** | 架构发现先于通道设计；没有万能通道 |
| **勘误文化** | 判例可翻案、里程碑可自我纠正，全部记录在案 |

# 02 · 文件体系与编辑器行为

> 证据：[A][J]。这一篇描述编辑器**如何对待你的文件**——比格式本身更容易踩坑的部分。

## 1. 三文件结构

一张本地地图在磁盘上有三处镜像：

| 文件 | 角色 |
|---|---|
| `<mapId>/<mapId>.gil`（主文件） | 关卡文档（实体区 + 图库 + 变量注册表） |
| `<mapId>/beyond_level_slice/<mapId>_N.gis` | 分片（图定义的数据源，推送链路消费——见 docs/21 §2 对账注） |
| `Temp/<mapId>.gil` | 工作副本 |

另有 `<mapId>.gilh`（地图实体索引）与 `Player.gip`（**云端地图列表的本地缓存**——地图的"户口"在云端，本地删除游戏内地图后本地文件会变成孤儿）。

> **v1.3 对账注**：编辑器进程在装载期**不直接读这些文件**（文件系统监控实证）——分片与主文件是**游戏侧**组推送数据的数据源，内容经推送进入编辑器（完整数据流定律见 docs/21 §2）。"分片是加载来源"指的是推送链路的上游，不是编辑器的文件读取。

## 2. 保存与落盘时机 [J]

- 编辑器内"保存" → 上传**云端**；
- 退出编辑器 → 本地文件**不变**；
- **完全退出游戏 → 本地三文件才落盘**；
- 补充判例：当前打开图的工作画布内容，经保存 → 退关重进 → **存活**（画布路径可持久化，docs/21 §6）。

想读取"编辑器眼中的最终状态"，必须等游戏整体退出后再读盘。

## 3. 编辑器行为六定律

以下全部为可复现实验判例 [J]：

1. **静默降级**：编辑器、导入器、运行时三层对内容问题**全都不报错、不弹窗、不留日志**。错误的唯一表达方式是"东西不见了"或"保存后变了"。
2. **三级判定**：对任意内容，编辑器的处置只有三档——解析异常=丢弃；解析成功但字节冗余=接受并在保存时规范化（缩水）；字节完全规范=恒等接受。
3. **只存不改**：编辑器保存时对既有内容**原样保留**——不重排引脚、不补默认、不纠错。你给它的错误字段它会忠实地存回去。
4. **值随型走**：带值的泛型引脚切换类型时，值必须同步转换或置空；只换类型标记保留旧值 → 编辑器规范化时丢值。
5. **严格同型连线**：数据连线的两端类型必须严格一致（int↔float 互连在真实语料中零出现）；类型错配的连线在**加载时被静默丢弃**——保存时它还在字节里，重开就消失。
6. **会话内按序渲染、重载按索引解析**：引脚实例顺序在会话内决定显示位置，但加载时按 PinSignature 的 index 对号入座——索引错位一格，值和连线全部落错槽或消失，且无任何提示。

## 4. 推论：如何安全地研究格式

- 验证修改是否被接受：对比"你写入的字节"与"游戏退出后落盘的字节"。一致=恒等接受；变短=被规范化（差异即规范化规则）；内容缺失=被丢弃。
- 归纳格式规则必须用**编辑器从零原生创建**的样本。编辑器保存过的第三方内容会原样保留第三方的错误——被污染的样本会循环验证你的错误（本项目曾因此把"引脚索引从1起"的错误规则保持了两天，直到原生样本对照才翻案）。

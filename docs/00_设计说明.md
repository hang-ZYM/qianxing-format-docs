# 设计说明：这份文档为什么长这样

> **读者为什么需要知道这个** —— 这份文档不是按"我们发现的顺序"写的，是按"你能读懂的顺序"排的。先花两分钟知道它怎么组织，后面会省很多时间。

**前置**：无。这是整份文档的第一篇。

---

## 一、这个仓库在做什么

千星奇域是《原神》的 UGC（用户创作）系统。它是一个**封闭系统**：没有 SDK、没有公开文档、没有源码。想在里面做出复杂的东西，只有两条路——手工在编辑器里点，或者**把它的数据格式读懂，然后直接生成**。

这个仓库是我们走第二条路的成果，**分两侧**：

- **左岸 · 对「游戏」的处理** —— 那个封闭系统的数据格式：容器、字段、组件、节点、实体、环境、地形……
- **右岸 · 对「项目」的处理** —— 我们自己的关卡项目：它由什么构成、怎么拆成模块、怎么拆成可验证的步骤

两侧之间靠**对齐**连着：右岸的每一个设计决定，都要落到左岸某个**可行位置**上。

> **左岸是"理解"，右岸是"设计"。左岸你只能发现真理，右岸你可以创造结构。**

---

## 二、为什么是"两侧"而不是"一本手册"

因为这两侧的**性质根本不同**：对象、能动性、动作、变化速度四项的对照表见 [03 两岸一桥](03_两岸一桥.md) 第二节（权威版本）。

把它们混在一起写，结果是读者分不清**哪些是"世界的事实"，哪些是"我们的选择"**——而这两件事的可信度和可改动性完全不同。

## 三、四条写作原则

### 原则 1 · 一个概念只解释一次
所有自造概念集中进 **[术语表](参考_术语表.md)**，正文首次出现时给一句定义 + 一个例子。

### 原则 2 · 每个单元回答"读者为什么需要知道"
每篇开头都有一句话说明：它在解决什么问题、不读会怎样。

### 原则 3 · 论必有据，且标注证据等级

| 等级 | 含义 |
|---|---|
| **字节实证** | 从真实文件里读出来的 |
| **官方文档** | 官方语料 / 编辑器界面里的原文 |
| **人工核验** | 人在编辑器或实机里亲眼确认过的 |
| **推断** | 我们的推理，**尚未验证** |

**这一条是我们最坚持的东西。** 逆向类文档最常见的问题是把推测写成事实；把证据等级标出来，读者才知道该信到什么程度。

### 原则 4 · 诚实
**未完成项、失败路径、试过但没成的路，照写。**
一份说"我们不知道 X、试过 Y 失败了"的文档，比一份什么都敢说的文档可信得多。没验证的东西进 [未完成项台账](参考_未完成项.md)，不混进正文当结论。

## 五、三条阅读路径

同一份文档，三种人读法不同。**挑一条走，不要从头读到尾**：

| 你是 | 你关心 | 走这条 |
|---|---|---|
| **创作者**（想做一个千星关卡） | 能做出什么、怎么开始 | README → 12 分钟跑通 → 右岸 05 → 左岸 10 → 按需查 `手册/` |
| **AI / 自动化工程师**（想做类似的事） | 为什么这么搭、怎么复用 | README → 01 → 02 → 03 → 06 → 07 → 12 |
| **逆向 / 数据开发者** | 字节长什么样、怎么自己挖 | README → 09 → 11 → `手册/` |

## 六、开放范围

这个仓库**开一部分、不开一部分**，边界是明确的：

**开**：世界的事实（左岸）、方法（右岸的工程层）、可独立使用的工具
**不开**：**关卡成品本身**（那是作品，不是方法）、以及任何与进程内操作、绕过机制相关的手段

**但关卡的设计过程会作为案例写进右岸**——讲方法，不讲成品：

- 会写：为了做到某个效果，我们试过哪几条路、为什么最后选了这条
- 不写：关卡文件、具体场景布局、坐标与数值表

一句话：**开"怎么搭"，不开"搭了什么"。**

说明边界本身就是一种专业——读者知道哪些事这里不讲，也就知道该信到什么程度。

# 模块化：域怎么切、模块长什么样

> **读者为什么需要知道这个** —— 右岸要处理一个复杂创作，先得回答两个工程问题：**把产物切成几块**（域），**每块长什么样、怎么调**（模块）。这一篇给的是这两件事的规格，不是心得。不读它，后面 [07 任务分解](07_任务分解.md) 里"每个任务 = 一次模块调用"就没有可调用的东西，08 状态（尚未写出）里的日志与版本也不知道在管谁。

**前置**：[03 两岸一桥](03_两岸一桥.md)。左岸的落点细节见左岸部分（09–11）与 `手册/`；本篇只用到落点的**名字**，不展开字段。

## 一、域是怎么切的

### 切分依据：三个判据同时成立

一个域不是"一类功能"随手划的，是三个条件同时成立才成立：

1. **有独立落点**——它在左岸能指认出一族字节位置（f5 实体名册、f10 图库、f7 地形组、f15 资产库、`.gia` 元件方言……）。落点是左岸的**事实**，不是我们发明的位置。
2. **有独立校验器**——它的产物能有一个出口判定，不用人看一眼才知道对不对。没有校验器的"域"只是一堆字段。
3. **是版本叠加单元**——一个域的一次操作失败，可以不污染别的域（各域往同一份关卡上叠加各自的 layer）。

这三条里，**第 2 条是硬约束**。它决定了切出来的粒度：一个域的大小，等于"这批字节**必须一起写、且必须一起验**"的最小集合。

### 切出来的域

| 域 | 左岸落点（字节位置族） | 叠加/版本单元 | 公开仓 `mods/` 里的模块 | 状态 |
|---|---|---|---|---|
| **关卡** | `.gil` 整体 + f11 关卡设置主存储 | 整文件一个版本 | `level.mount` / `level.deploy` / `level.judge` / `level.checkpoint` / `level.rollback` / `log.query` | ✅ |
| **实体** | f5 放置实体条目 + f6 树 tab3 叶（另有 f4 模板实体库、f8 布设组） | 一次放置 | `entity.place` | ✅ |

### 为什么按这个维度切，而不是按别的

有三种看似更自然的切法，都不成立：

- **不按"操作类型"切**（增 / 删 / 改）。同一批字段在增删改三种操作下走的是同一个校验器，按操作切会把同一个校验器拆成三份，重复。
- **不按"用户意图"切**（"做一只隐身怪" / "让玩家看不远"）。意图的粒度与字段的粒度差数量级——"让玩家看不远"在字节层是四个独立旋钮（见 [03](03_两岸一桥.md) 第三节）。意图切出来的单元**没有独立校验器**，也就无从判定对错。
- **不按"文件/容器"切**。一个 `.gil` 里同时装着实体、图、地形、资产引用；按容器切，一次失败就全关回滚，粒度太粗。

选"落点族 × 校验器边界"这个维度的直接动因是**失败可归因**：产物出问题时，要能定位到**唯一一个域**、从而定位到唯一一个校验器。域就是校验器的作用范围，这是本项目的四判据里排第一的那条（可归因 / 可回滚 / 可复现 / 可看完）。

域的大小也有反例可举。"图在库但没挂载 = 永远不执行"——图装进 f10 图库、挂到宿主 f6.f13、注册进资源树 f6 树4、实体注册面登记，这四件事**必须一起做完、一起验**，所以它们同属一个域（关卡/图），不能拆成四个更细的域，否则每拆一步都产生一个"看起来对、实际是死的"中间态。

## 二、模块长什么样：契约四要素

### 一个模块 = 一个可调用函数

签名类型化，返回统一对象 `Result`。`graphgen.build(logic, name, guid) -> BuildResult`、`level.mount(graph_gis, host_guid, graph_guid, category) -> MountResult`、`terrain.patch(level_name, cells) -> Result` 都是这个形态。

### 四要素就是事务的四个要素

每个模块内建四件事，它们不是"检查清单"，是一个**事务**的四个要素：

| 要素 | 事务语义 | 在代码里 |
|---|---|---|
| **前置检查** | 事务开始前的不变式 | 不满足 → 抛 `PreconditionError` |
| **执行** | 事务体（确定性代码，同输入必同输出；**不在此环节调用 AI**） | 模块的函数体 |
| **后验** | 提交条件 | 不满足 → 抛 `ModuleRejected` |
| **回滚** | 失败时回到事务前的状态 | 由 `core.py` 包装器保证（拒绝时不落盘新版本） |

四要素凑齐，得到的是一个二值结果：**要么提交一个新版本，要么什么都没发生、并且拿到原因**。没有第三种结果。

### 两种失败，两种语义

这是四要素里最容易被写错的一处，也是它区别于"检查清单"的地方：

- **前置不过 = 换路，不算失败**。条件不满足不是错误。`PreconditionError` 不计失败、不计拒绝，编排器换一条路。
- **后验不过 = 自动回滚 + 计一次失败**。事情已经做过，结果不对，必须回滚并记账。`ModuleRejected` 不产新版本，并累加连续拒绝计数。

**为什么这个区分重要。** 它给了编排"零成本试路"的能力。前置是"看条件"，几乎零成本；如果把条件不满足也记成失败，编排器会在一条根本走不通的路上反复"重试"，烧掉预算。反过来，后验失败是已经动过手的，必须计失败并回滚，否则失败履历失真。

落到具体例子上（都可以在 `mods/` 源码里对上）：

| 调用 | 前置不过（换路） | 后验不过（回滚 + 计失败） |
|---|---|---|
| `level.mount` | `host_guid` 不是 S0 唯一宿主 `0x41400001`；`category` 不在 f501 四值挂载空间 | 出口校验 V0-V7 有 FAIL；`graph_guid` 与图头 f5 不符 |
| `terrain.patch` | 目标格不在底座（空格 = 虚空，不支持造块）；批内互斥律冲突 | 块数交叉核对不等；输出往返验证失败 |
| `env.set` | 关卡无当前版本（先入库）；真实样本图不在位（无预设可移植） | 读回字段与请求不符 |

### 换路信号：连续被拒的阈值

同一个模块**连续 4 次**被后验拒绝，抛 `ConsecutiveRejectError`，编排器必须换路：

```
# mods/core.py
REJECT_LIMIT = 4  # Voyager 律：同模块连续 4 次拒绝 → 编排器换路
```

计数在内存里（`_rejects`，按模块名），一次成功清零，换路后清零；操作日志留全量证据。`4` 是经验值，关键不是这个数，是**重试上限必须存在**——第 5 次重试的期望收益趋零，机会成本是整条产线停摆。

## 三、为什么"坏调用从构造上产生不了新版本"

这是有四要素之后被**结构保证**、而不是靠人自觉的一条不变式。机制在 `mods/core.py` 的包装器里，不在模块里：

1. **模块不写版本**。模块只把产物写进临时槽（`state/tmp` 槽，在版本域 `levels/` 之外），把路径放进 `Result.artifact` 返回。落盘新版本是包装器的事：全过后才 `commit_version(level, src)` 复制字节成 `v<N+1>.gil` 并更新 `current.json` 指针。
2. **拒绝发生在落盘之前**。装配、手术、校验全在临时槽完成；后验一旦 FAIL，包装器走拒绝分支，版本指针一动不动。
3. **宣称的产物必须真的存在**。模块若返回 `artifact` 但文件不在，包装器按拒绝处理（"宣称的产物不存在 = 后验事实不成立"）。
4. **落版后字节守恒复核**。包装器把 `v<N>.gil` 的字节与产物字节逐字节比对，不一致直接抛 `RuntimeError`——这是基础设施事故，响亮失败，不静默降级。

四条合起来得到的恒等式是：**日志的最后一版 = 最后一个已知好状态**。坏调用没有路径能产生新版本，所以"产物任意时刻都有效"从纪律变成了数据结构性质。

**代价。** 每次 PASS 都要复制一份全量字节存成新版本，`.gil` 可能是 MB 级，版本目录会随操作次数膨胀；同时模块作者要写两组校验（前置 + 后验），写模块比写一次性脚本贵。项目接受这两条——版本目录落在 `_state/` 下并进了 `.gitignore`（运行产物不入库），而多写的后验正是把"离线能拦住"变成资产的那部分投入。

## 四、怎么加一个新模块

入库五条标准（缺一不入，见 `手册/30` §6）：审计先行 → 实现（含四要素）→ 真实样本自证（好件全过 + 缺陷样本全拦）→ 诚实状态位 → 遗留清单。

要动的地方是固定的几处：

1. **加函数**：`mods/<域>.py` 里加一个 `@core.module("域.动作")` 的函数，签名类型化，返回 `Result`。
2. **写两组校验**：前置把"状态不满足"的情形写全，后验取**该操作可达的最高级**（见 [07](07_任务分解.md) 第三节），判不了的级如实标 `PENDING-ANCHOR` / `PENDING-S1`，不美化。
3. **加自测**：`mods/test_<域>.py` 里加用例，**含负例**——好件全过、缺陷样本全拦，才算自证。
4. **走路径抽象**：凡是本机位置（游戏目录、工具树、状态根），经 `mods/config.py` 解析，代码里不出现任何绝对路径；缺环境时抛 `PreconditionError`（换路，不算失败）。
5. **改索引**：`mods/MODULES.md` 加一节（吃 / 吐 / 保证 / 现状）。
6. **标状态位**：✅ / 🔶 / ⏳ 三档，禁止过度声明完成度。

两条边界纪律：

- **副作用领地制**：一个模块只许写三处——当前关卡的新版本、自己的库、操作日志。不碰别的模块的领地。
- **≥2 次才固化**：创作中反复出现的子任务才值得做成模块（过早抽象的维护成本高于重复劳动）；一次性意图不强行模块化。

**代价。** 这套门槛让写模块明显比"这次先手动搞一下"慢；收益是能力沉淀在库里而不是散落在会话里——没有这条纪律，前一条慢就没有回报。

## 五、失败语义：换路 / 修 / 停

四要素把失败分成四类，动作各不相同：

| 失败种类 | 触发 | 语义 | 动作 | 损失 |
|---|---|---|---|---|
| **前置不过** | `PreconditionError` | 此路不通 | 换路（改参数 / 换模块） | 零 |
| **后验不过** | `ModuleRejected` | 这一步做坏了 | 自动回滚 + 计失败；连 4 次 → 换路信号 | 一步 |
| **意外崩溃** | 其他异常 | 代码 / 基础设施 bug | 落日志后**原样上抛**（响亮失败），不计拒绝 | 停下修 |
| **运行级判败** | `Verdict.passed = False` | 产物有效，行为不对 | **不回滚**；判决 + 观察数据回流 → 分解出修复调用 | 触发修复序列 |

三种处置要分清：**该换路**的是前置不过和连败；**该修**的是运行级判败（产物仍然是有效版本，改的是它）；**该停**的是意外崩溃——它不该被任何自动重试吞掉，必须抛上来让人看见。

这也是"响亮失败"这条纪律的落点：`core.py` 对意外异常的处理是先落一条 `kind="error"` 日志、再原样 `raise`，绝不降级成一次"拒绝"混进正常失败里。

## 可验证的把手

1. **阈值与分支**：`mods/core.py` 的 `REJECT_LIMIT = 4`、`run_module` 的三种异常分支、`commit_byte_equal` 检查——本篇第二节、第三节、第五节的每条断言都对应这里的某几行。
2. **两种失败的站点**：`grep -n 'PreconditionError\|ModuleRejected' mods/*.py`，每个域的前置/后验写在哪里、判什么，一目了然。
3. **域表的状态位**：`mods/MODULES.md` 的每节"现状"行；公开仓实际发布面见 `mods/README.md`（模块一览表）。
4. **自测**：`python -m mods.selftest`（CORE 必跑；FULL 缺环境如实 SKIP）。

## 未确定项

- **环境域档位与生效机制未定案**：`env.set` 只支持真实样本中少量具名预设；其余档位未采，环境生效机制未在编辑器实测（见 `mods/env.py` docstring 遗留项）。
- **组件域的后验判不了语义正确**：组件 cid 与官方组件名的**系统对号尚未完成**（只有 cid5 / cid8 / cid11 / cid14 / cid21 / cid27 / cid42 等少数据可靠对号），因此 `component.attach` 的后验只能判"载荷逐字节一致 + 实体数不变 + 形态门"，**判不了"这个组件真的是你以为的那个组件"**（推断，见架构正典的待核项）。
- **域粒度不是唯一解**：本篇的切法由"校验器边界"定，若校验器能力变化（例如某域补上运行级判定），域的合并或拆分需要重估（待补）。
- **"域"一词在本仓库有多种用法**：内容域（本篇）、版本域（`levels/<名>/`）、号域（guid 高 16 位）。本篇一律用"内容域"义（对照 `参考_术语表.md` §1.1）。
- **另一条通道不在公开范围**：除本条交付链，还有一条只用于单模块自检的进程内通道，涉及编辑器进程内操作，按 [00 设计说明](00_设计说明.md) 第六节不开。

## 三、易混词辨析

> 只收录**在本仓库里实际出现过、且容易混淆**的词对（含仓库自身的用词不统一）。

**3.1 元件 vs 实体 vs 组件**
- **元件** = 模板（章），号在 `0x40C` 段，是"章谱"；**实体** = 盖出来的印，号在 `0x404/0x408` 段，
  是场景里的具体对象；**组件** = 挂在实体身上、用 cid 标型号的功能零件。三者是"模板 → 实例 → 零件"三层，
  但都带 guid，初读最容易混。（定义见 §1.1；源头 `guide/概念指南.md` §1. 元件（0x40C）—— 盖章的章 / §3. 组件（cid）—— 对象身上的功能零件。）

**3.2 六槽模型 vs 实体四槽**（**2026-10-15 定案：统一为「六槽模型」**）
- **规范**：实体消息共**六个字段**（f1 guid / f2 来源标记 / f5 行为 / f6 编辑器 / f7 资源 / f8 尾字段 asset_id）
  → 称「**六槽模型**」（`手册/03_数据模型总表.md` §1. 实体（六槽模型）[A]）。
- 其中**承载组件列表的只有 f5/f6/f7 三个组件槽**；**f8 是尾字段（asset_id varint）**，不是组件槽
  （`手册/03` §1"f8: aid"、`手册/29` §2. 反向提取：字段路径（gia_extract.py 的依据）"f8: asset_id (varint)"、`manuals/02` §二、实体字节规范、内部正典 01b §一，四处一致）。
- 旧称「实体四槽」（`手册/11` §1. 组件系统定律 [A]、`手册/12` §0. 组件系统定律（先读这个）、`manuals/02`、`manuals/08`、`手册/20` §3. 设置群 cfg（`f75.f1.f1`）字段表）把 f8 误算作第四个组件槽——
  其自带组件表（`手册/12` §1、`manuals/08` §一）也**只列 f5/f6/f7 三行**，可见"四槽"是残留标签，**已废**（相关篇目已改）。
- 引用口径：只说"六槽模型"（指整个消息）或"组件槽 f5/f6/f7"（指部件位），**不再用"四槽"**。

**3.3 装载 vs 挂载**
- **装载** = 平台（游戏/编辑器）**读入**文件、接受内容（L3 装载级验收、"游戏装载接受"）；
- **挂载** = 把一张**图装到某个实体上**（`level.mount`），是关卡内的动作。
- 一句话：装载是"平台读文件"，挂载是"图接实体"。

**3.4 版本 vs 快照**
- **版本** = 通过验收后落下的存档槽 `v<N>.gil`（加 `current.json` 指针）；
- **快照** = 某一时刻状态的**拷贝/读数**，散见于多处（"启动时刻快照""五字段快照逐格相等"）。
- 一个是受版本制管理的实体存档，一个是任意时点读数；不可互称。
- **版本快照**（新收，见 §1.5）= `level.checkpoint` 的产物（`v<N>.gil` ＋ 指针更新）：把某一时刻的关卡字节**落成版本存档**。

**3.5 号域 vs 段 vs 段位律**
- **号域** = 概念（guid 高 16 位 = 类型域）；**段** = 号域的具体取值（`0x404` 段）；
- **段位律** = "段放错不显示"这条规则。三者同源不同层，正文里常被混着说。

**3.6 后验 vs 校验（verify）vs 三层校验**
- **后验** = 模块**产出后的自动验收**（四要素之一）；
- **校验（`qxfmt verify`）** = 具体的**规则面**离线检查（能拦已知缺陷，**不等于**装载判定）；
- **三层校验** = 概念更大的三层体系（写入自校验 / 规则校验 / 编辑器终审），后验用的是它。
- 三者是"机制 / 工具 / 体系"的关系。

**3.7 编排者 vs 编排器**（**2026-10-15 定案：统一为「编排器」**）
- 规范词 = **编排器**：内部正典名（`02b_任务分解架构设计书_v3.md` §六标题"编排器"），
  代码（`mods/core.py` 的 `PreconditionError` 文档串 等）、`guide/模块参考.md` §2. core —— 基础设施（被调用，不是业务模块）、新主线 `docs/06` `docs/07` 均用此。
- `手册/30_任务分解与模块化方法论.md` 原有 5 处"编排者"（:28,47,53,68×2,146），已于 2026-10-15 **全部改为"编排器"**。

**3.8 底座 vs 骨架底座 vs 基底**
- 都指"**作为装配基础的关卡样本**"：`mods/README.md` 里同一物在相邻几行内写成"骨架底座样本"
  （:42）与"底座"（:37）。建议统一为"**基底关卡样本**"。

**3.9 金样本 vs 真实样本**
- **同一概念的新旧两种叫法**：旧文（`guide/模块参考.md` §0. 配置：状态根、游戏目录与环境变量 等）叫"金样本"，新定名是"真实样本"。
  见 §2 第一行。

**3.10 第四要素：回滚 vs 日志**（**2026-10-15 查代码定案：不是两个名字，是同一事务的两条分支各写了一边**）
- 查 `mods/core.py` 的包装器 `run_module`（:186-217）确认，实际是一个**二分事务**：
  - **通过 → 提交**：`commit_version()` 落新版本（`v<当前+1>.gil`）＋ `_append_oplog(kind="ok")` 写日志（并复核字节守恒）；
  - **拒绝 → 回滚**：抛 `ModuleRejected` → `_reject()`，**不落新版本、版本指针一动不动**（"拒绝发生在落盘之前"，
    产物先在临时槽 `state/tmp`）＋ 写一条 `kind="rejected"` 日志。
- 所以：**日志**两条分支**都写**（oplog 有 ok / rejected / precondition / error 四类行），它不是"通过分支"的专属；
  **回滚**是**失败分支**的语义（实现＝"不落版本／不入账"；另有显式 `level.rollback` 做版本指针回拨）。
- 两者是**同一事务终态（提交 / 回滚）的两面**——`手册/30` 的"回滚"记了失败面，`mods/README` 的"自动日志"记了横切记录面。
  故第四要素**规范名取「提交 / 回滚」**（提交＝写日志＋落版本；回滚＝不落版本，日志两条分支都记），三处已据此统一：
  `docs/06 模块化 第二节` 表、`mods/README.md` §模块一览、`guide/模块参考.md` §1. 全家福。
- ⚠ 附带澄清：`docs/06 模块化 第二节` 与 `docs/06` 都把后验不过写成"自动回滚"；**代码的事实是"不入账"（不落版本）**——
  语义等价（回到调用前），并非另一次动作。

**3.11 定义体 vs 成员体 vs 实例**（**2026-10-15 已补定义**）
- **实例**在仓库里大范围在用（节点实例、控件实例、实例化）；**定义体 / 成员体**是元件对象模型的词，定义见 §1.5。
- 三者关系：**定义体**是"模板侧结构"（`.gil` f4 元件定义条目），**成员体**是元件组里**成员**的那份定义体，
  **实例**是"实例侧对象"（由模板盖出来的具体一份）。它们是"模板侧结构 vs 实例侧对象"的关系，
  与 §3.1 的"元件/实体"是同一层意思，勿叠成两层混淆。

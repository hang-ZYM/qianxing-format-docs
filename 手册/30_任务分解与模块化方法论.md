## 1. 问题：端到端生成为什么必然失败

设生成一张可玩关卡要经过 n 个环节（合成容器、构造节点、装配引用、通过装载、运行正确……），
每个环节的独立合格率为 p：

- 端到端一次生成的合格率 = p^n——p=0.9、n=10 时只剩 35%，且 n 随作品复杂度只增不减；
- 封闭格式的独特恶化因素是**静默降级**：平台对坏内容的表达不是报错，是"东西不见了"
  （手册/02 定律 1）。错误不在发生点暴露，而是传播到链条末端，以"整体不对"的形式出现；
- 于是端到端失败后**无法归因**：十处嫌疑、零条线索，修复循环不收敛。实践中表现为 AI
  反复重新生成整个产物，每次修好一处、换坏另一处。

结论不是"生成能力不行"，是**结构不行**：验收点只有一个（终点），而复杂度要求验收点
分布到每一环。方法由此确定——任务分解 + 逐步验收。

## 4. 验收分级：后验取可达最高级

| 级 | 名称 | 判什么 | 本仓库对应 |
|---|---|---|---|
| L1 | 字节级 | 写出的字节可被自己的解析器往返复现（encode(parse(x))==x） | `qxfmt roundtrip` |
| L2 | 结构级 | 满足已积累的实证格式规则 | `qxfmt verify` |
| L3 | 装载级 | 平台装载接受，内容逐节点存活（节点级对照，手册/06 §10） | 导入观察 + 重保存对比 |
| L4 | 运行级 | 执行语义符合预期（执行记录逐条回读） | 手册/23 的观察面 |
| L5 | 人审 | 视觉/体验验收 | 用户 |

原则：

1. **每个操作的后验取它可达的最高级**——能判 L2 的操作不要停在 L1。分级不是形式，
   每一级都要有机器可读的判据与判定记录；
2. **判级要诚实**：L2 全绿 ≠ L3 会过。本项目实测四类异常离线校验全 PASS、装载后内容
   仍被剥（手册/28 §1.2）——"知道自己不能判什么"与能判什么同等重要；
3. 若平台提供快速判定通道（本项目图域有概念级描述，手册/28 §三），把它作为该域操作的
   首选后验——验收回路越短，修复循环收敛越快；
4. L5 不可外包给机器：机器产出判据与证据（预写"看到 X = 判 Y"），人只做终审。

## 5. 仲裁规则：金样本字节 > 文档断言 > 枚举名

三条证据来源冲突时按此序仲裁：

| 来源 | 是什么 | 为什么排这个位置 |
|---|---|---|
| 金样本字节 | 平台原生创建/接受的产物的实际字节 | 平台自己的输出，最高权威 |
| 文档断言 | 逆向笔记、schema 注释、手册记载 | 可能过时，可能本来就是错的 |
| 枚举名 | 从名字/编号归纳的对应关系 | 最弱——名字是研究者贴的标签，会继承被检验的假设 |

**真实翻案案例**（本项目 2026-10 的审计记录）：

- 立法：某资产库条目的配置段存在"段号 k → 载荷字段 k+10"的偏移律，两个域共 14/14
  样本吻合，立为定律写进卡片；
- 翻案：按金样本做全档扫描，反例遍地——42→f55、70→f75、21→f30、6→f21、73→f78、
  8→f16（职业条目自己就是 +8）；另一批 39→f49、35→f45、1→f11 恰好吻合；
- 复核结论比翻案本身更疼：所谓"14/14"的验证过程有缺陷——职业条目自身 10 段中至少
  4 段不符，当时**不可能**全验过。定律是在没数清样本的情况下立的；
- 双源定案：反编译读出的字段写盘序号（机器事实）+ 资源树条目与资产库条目按 guid
  三向对账，独立证实偏移并无规律。

三条教训（与 [手册/06](06_验证方法论.md) 元律 M2/M3 同源）：

1. **吻合不是验证**：14 个样本吻合只说明"没找到反例"，不说明"定律成立"；
2. **同源证据不叠加**：14 个样本若来自同一种归纳方式，证据力等于 1 个样本；
3. **金样本一票否决**：字节反例存在即翻案，无论文档写得多自信。

## 6. 操作库的成长制度

操作库是这个方法论的资产。成长制度四条：

1. **入库五条标准**（缺一不入）：

| # | 标准 | 内容 |
|---|---|---|
| 1 | 审计先行 | 实现前先对正典（平台原生金样本）出差异清单——先弄清要仿什么 |
| 2 | 实现 | 确定性代码 + 四要素契约完整（§3） |
| 3 | 金样自证 | 好件全过 + 病件全拦（对抗测试集，手册/06 §9） |
| 4 | 诚实状态位 | PASS / 待验证 / 未实现——禁止过度声明完成度 |
| 5 | 遗留清单 | 已知边界与未决问题随操作卡入档 |

2. **≥2 次复现才固化**：创作中反复出现的子任务才值得做成操作；一次性意图不强行
   模块化（过早抽象的维护成本高于重复劳动）；
3. **一操作一卡**：接口、契约、测试判据、遗留问题，入库时建卡——卡片是操作库的
   文档形态；
4. **只许调用库内操作**（§3 边界纪律的重申）：这是制度的关键一条——没有它，能力会
   以"这次先手动搞一下"的形式流失掉。

## 8. 与本仓库的关系

本仓库是这个方法论的静态投影：

| 方法论构件 | 本仓库实现 |
|---|---|
| L1 字节级验收 | `qxfmt roundtrip`（容器与树往返验证，[QUICKSTART](../QUICKSTART.md)） |
| L2 结构级验收 | `qxfmt verify`（实证规则离线校验，compose 时自动执行） |
| 验收边界测绘 | [手册/28](28_验证方法与发现.md) §1.2（离线判不了什么，与能判什么同等重要） |
| L4 运行语义基准 | [手册/23](23_运行语义实证.md)（"写对了"在运行时的含义） |
| 金样本与模板 | [手册/22](22_最小图正典与模板.md)（编辑器原生最小图 = 正典起点）+ `templates/` |
| 操作单元的公开文档形态 | [manuals/](../manuals/00_目录与使用说明.md)（22 册任务导向操作手册，按任务查册） |

给想复制这套方法的读者一句话：**先建验收，再建生产**。规则从平台行为回填离线校验
（手册/28 §一），让每一类犯过的错误此后都能在本地拦截——这是整个体系里唯一只会
单调增长的资产。
